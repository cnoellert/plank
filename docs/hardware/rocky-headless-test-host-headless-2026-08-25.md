# Rocky Linux headless-test-host Headless Display Qualification - 2026-08-25

## Scope

`headless-test-host` at `192.0.2.105` is the dedicated StationConnect headless-display
test host. These probes did not alter `hardware-test-host`. The work qualified NVIDIA/Xorg
virtual outputs, XRandR/Xinerama enumeration, depth-30 direct OpenGL, and
NvFBC-to-CUDA capture without a physical monitor or dummy dongle.

The probes did not qualify Flame, GDM-to-user login, StationConnect packaging,
the x264 encoder, client decoding, Wacom, or multi-hour reliability. The
StationConnect host package was not installed on `headless-test-host` during these tests.

## Driver Contract

The exact NVIDIA 580.159.04 documentation installed at
`/usr/share/doc/NVIDIA_GLX-1.0/` states:

- `AllowEmptyInitialConfiguration`, `MetaModes NULL`, and
  `UseDisplayDevice none` expose no RandR displays;
- software requiring RandR displays should use `ConnectedMonitor` to simulate
  a physical display;
- `CustomEDID` supplies mode and identity data for simulated display devices;
- comma-separated specific DFP identifiers may simulate several outputs;
- `UseDisplayDevice` selects which detected or forced devices belong to the X
  screen.

The selected design therefore uses `ConnectedMonitor`, `UseDisplayDevice`,
`CustomEDID`, and an explicit `MetaModes` layout. It does not use
`UseDisplayDevice none` for the product topology.

## Results

### Two virtual 1920x1080 outputs

The transient Xorg server exposed:

```text
Screen 0: 3840x1080
DP-0: 1920x1080+0+0, primary
DP-2: 1920x1080+1920+0
Xinerama head 0: 1920x1080 @ 0,0
Xinerama head 1: 1920x1080 @ 1920,0
```

The Xorg log confirmed depth 30, RGB weight 10:10:10, both custom EDIDs, both
connected outputs, and the exact validated metamode. Direct rendering used
`NVIDIA RTX A5500/PCIe/SSE2` through OpenGL 4.6.

NvFBC 1.9 reported XRandR available, screen `3840x1080`, two outputs with the
same rectangles, BGRA8888 CUDA-device capture, no CPU readback, 60.00 forced
capture calls/s, no driver-missed frames, capture p95 between 22 and 25 us,
and no deadline misses.

### One virtual 3840x2160 output

NvFBC reported one `DP-0` output at `3840x2160`, a 33,177,600-byte BGRA frame,
60.00 forced capture calls/s, 39 us capture p95, 69 us maximum capture time,
zero driver-missed frames, and zero deadline misses.

### Two virtual 3840x2160 outputs

The X server and NvFBC both reported:

```text
Screen 0: 7680x2160
DP-0: 3840x2160+0+0, primary
DP-2: 3840x2160+3840+0
```

NvFBC captured a 66,355,200-byte BGRA CUDA frame at 60.00 forced capture
calls/s with 37 us p95, 67 us maximum capture time, zero driver-missed frames,
and zero deadline misses. This proves capture feasibility only. Dual 4K is not
qualified for x264 encoding or the client's exact-profile software decoder.

### Real GDM configuration-directory overlay

An overlay was linked temporarily at
`/etc/X11/xorg.conf.d/99-stationconnect-headless-probe.conf`. Its
`DefaultServerLayout` selected the StationConnect screen while Xorg continued
to load `/etc/X11/xorg.conf` and the canonical global input classes. Under the
normal GDM command line, the result was:

- two 1920x1080 RandR outputs and two matching Xinerama heads;
- depth 30 and a `3840x1080` virtual screen;
- direct NVIDIA OpenGL;
- NvFBC screen and output rectangles matching XRandR;
- 60.00 forced capture calls/s, 91 us p95, no missed frames, and no deadline
  misses.

The overlay was removed and GDM was restarted into its original configuration
after the probe.

### Packaged display-preparation helper

The candidate production helper generated the same configuration from a
temporary StationConnect INI containing `virtual_outputs = dual-horizontal`
and `virtual_mode = 1920x1080`. It ran only after GDM stopped, then normal GDM
startup produced two independent 1920x1080 outputs, a 3840x1080 X screen,
depth-30 direct NVIDIA rendering, and matching NvFBC output rectangles.
NvFBC completed 120 forced calls at 60.00 calls/s with 88 us p95, 116 us
maximum capture time, zero driver-missed frames, and zero deadline misses.

The helper's cleanup removed only its marked overlay. GDM returned to the
physical one-monitor layout, and `/etc/X11/xorg.conf` retained SHA-256
`2ecfcd68f51b8c47b8d9dfea8d73f6a20a57faddf0fa995956b4749451c3ecb8`.

### Rejected integration approach

Passing an absolute or search-relative `XORGCONFIG` environment variable to
`gdm.service` was ineffective. The environment appeared in the service, but
GDM's Xorg still logged:

```text
Using config file: "/etc/X11/xorg.conf"
ServerLayout "XFree86 Configured"
```

The probe expected two outputs, observed the canonical layout, failed, removed
its runtime systemd drop-in, and restored GDM. Production must not rely on an
`XORGCONFIG` environment override.

## Selected Direction

Use a StationConnect-generated file in `/etc/X11/xorg.conf.d/` with a unique
device, screen, and layout plus `DefaultServerLayout`. Preserve Autodesk's
canonical configuration and global input classes. Keep all StationConnect
screens at depth 30. The user explicitly authorized StationConnect to replace
or delete the active `xorg.conf` if later qualification demonstrates that a
configuration-directory overlay is insufficient, but replacement is not
currently necessary.

The production implementation still needs:

1. administrator-disabled-by-default INI settings and strict preset limits;
2. package-owned, reviewed EDIDs rather than the qualification copies;
3. an atomic overlay generator and systemd ordering before GDM;
4. active-session refusal and rollback behavior;
5. GDM-to-user login plus Flame visibility tests;
6. StationConnect host package and real stream tests;
7. exact-profile encode/decode, client presentation, input, Wacom, reconnect,
   and soak validation.

## Restoration State

After every probe:

- `gdm.service` was enabled and active;
- the transient `stationconnect-headless-xorg-probe.service` was inactive;
- `/tmp/.X11-unix` contained only GDM's `X0` socket;
- the probe overlay and GDM systemd drop-in were absent;
- no StationConnect host package was installed;
- `hardware-test-host` and the End-User NUC were untouched.

After qualification, the active `/etc/X11/xorg.conf` was deliberately reset
to an Autodesk-baseline configuration derived from
`/etc/X11/xorg.conf.dku_standard`. The only content changes are the four
`DefaultDepth`/`Depth` values from 24 to 30. The resulting active file has
SHA-256
`2ecfcd68f51b8c47b8d9dfea8d73f6a20a57faddf0fa995956b4749451c3ecb8`.
GDM then started normally at depth 30 with direct NVIDIA rendering.

The prior `nvidia-settings`-generated configuration remains available at
`/etc/X11/xorg.conf.pre-stationconnect-20260825` with SHA-256
`460c32a53b7387a89417d5210a8ec01061b52c492eb21e30a26a94863bc380f6`.
Production virtual-display support will overlay the Autodesk-derived baseline;
it will not modify that baseline for each requested topology.
